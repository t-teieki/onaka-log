## 3. 分かったこと

### 3-1. 条件のよい写真なら、どのモデルでも正確に読める

2枚とも、全モデル・全 effort で kcal・P・F・C・内容量を正しく読み取った（元サイズと 1024px）。**最も安い Haiku 5.5（1回約0.1円）でも精度は同じ**で、応答も 4秒前後。ただし今回の写真は比較的読みやすく、モデル間の差が出る条件（反射・曲面・小さい文字・切れ）は試せていない。

### 3-2. 「1個当たり」の表示は、基準量の数値がない

L001 の表示は「1個当たり」で、グラム数が書かれていない。全モデルが `basis.type = per_piece`、`basis.amount = null` と答えた。これは**プロンプトの指示（表示をそのまま転記し、推測しない）どおりの正しい読み取り**で、正解データ側が内容量（150ml）を基準量として書いていたため不正解と採点された。

アプリでは、次の規則で補えば正しく換算できる:
- 基準が「1個・1包装当たり」で量の記載がなく、内容量が読めていて個数の表記がない（1個売り）→ 基準量 = 内容量

### 3-3. 画像は長辺 1024px 程度で足りる

768px では1か所読み違えた（35.2 → 35.0）。1024px は元サイズと同じ結果で、入力トークンが約2割少ない。アプリでは**長辺 1024〜1568px に縮小**して送るのがよさそう（Lambda の 6MB 上限にも十分収まる: 1024px で約 200KB）。

### 3-4. 費用は入力が大半

元サイズの Sonnet 5.5 で、入力 5,441 トークン（約1.6円）に対し出力は約300トークン（約0.45円）。入力のうち画像は約2,200トークンで、残りは出力スキーマとシステムプロンプト。**スキーマとプロンプトは毎回同じなので、プロンプトキャッシュで下げられる可能性がある**（未検証）。

### 3-5. スキーマの不具合を1件発見・修正した

最初の実行で、全12回が API に 400 エラーで拒否された（費用なし）。原因は、null を許す enum を `"type": ["string", "null"]` と `enum` の組み合わせで書いていたこと。`anyOf` で書き直し、出力スキーマを v0.2 にした。同じ書き方を検出する規則を契約テストに追加した（[contracts/llm/README.md](../../contracts/llm/README.md) ルール6）。

## 4. 暫定の所見（判定保留）

- 合格の目安（条件のよい写真で 95% 以上）は、2枚では満たしている。ただし枚数が少なく、厳しい条件の写真がないため判定は保留する
- モデルの第一候補は **Haiku 5.5（effort low）**。精度が同じで、費用は Sonnet の約20分の1、Opus の約40分の1。厳しい条件の写真で差が出るかを確かめてから決める
- 画像は長辺 1024px 以上に縮小する

## 5. 次にやること

1. **条件の厳しい写真を数枚追加する（ユーザー）**: 反射・曲面（ペットボトルなど）・小さい文字・表示の一部が切れた写真・「100g 当たり」表示の商品。あわせて、栄養成分表示でない写真を1枚（`expected_status` = `not_nutrition_label`）。`poc/samples/label/` に画像と CSV の行を足す
2. 追加分で Haiku と Sonnet を比べる（費用は数円〜十数円。実行前に了承を得る）
3. 正解データの書き方を決める: 「1個当たり」のように量の記載がない表示は、`basis_amount` を空欄にする（採点を表示どおりにする）
4. プロンプトキャッシュの効果を確かめる（POC-44）
5. 結果がそろったら、モデル・画像サイズを ADR に残す
