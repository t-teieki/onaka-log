## 3. 分かったこと

### 3-1. 条件のよい写真なら、どのモデルでも正確に読める

1回目の2枚は、全モデル・全 effort で kcal・P・F・C・内容量を正しく読み取った（元サイズと 1024px）。最も安い Haiku 5.5（1回約0.1円）でも精度は同じで、応答も 4秒前後。

### 3-2. 「1個当たり」の表示は、基準量の数値がない

L001 の表示は「1個当たり」で、グラム数が書かれていない。全モデルが `basis.type = per_piece`、`basis.amount = null` と答えた。これはプロンプトの指示（表示をそのまま転記し、推測しない）どおりの正しい読み取りで、正解データ側が内容量（150ml）を基準量として書いていたため不正解と採点された。2回目からは、量の記載がない表示は `basis_amount` を空欄にしている。

アプリでは、次の規則で補えば正しく換算できる:
- 基準が「1個・1包装当たり」で量の記載がなく、内容量が読めていて個数の表記がない（1個売り）→ 基準量 = 内容量

### 3-3. 画像は長辺 1024px 程度で足りる

768px では1か所読み違えた（35.2 → 35.0）。1024px は元サイズと同じ結果で、入力トークンが約2割少ない。アプリでは長辺 1024〜1568px に縮小して送るのがよさそう（Lambda の 6MB 上限にも十分収まる: 1024px で約 200KB）。

### 3-4. 費用は入力が大半

元サイズの Sonnet 5.5 で、入力 5,441 トークン（約1.6円）に対し出力は約300トークン（約0.45円）。入力のうち画像は約2,200トークンで、残りは出力スキーマとシステムプロンプト。スキーマとプロンプトは毎回同じなので、プロンプトキャッシュで下げられる可能性がある（未検証）。

### 3-5. スキーマの不具合を1件発見・修正した

最初の実行で、全12回が API に 400 エラーで拒否された（費用なし）。原因は、null を許す enum を `"type": ["string", "null"]` と `enum` の組み合わせで書いていたこと。`anyOf` で書き直し、出力スキーマを v0.2 にした。同じ書き方を検出する規則を契約テストに追加した（[contracts/llm/README.md](../../contracts/llm/README.md) ルール6）。

### 3-6. 逆光で暗い写真でも、全モデルが正確に読めた（L005）

L005 は逆光で文字が暗く、斜めに写っている。それでも全4設定で kcal・P・F・C と基準量（1カップ 140ml）を正しく読んだ。Haiku 5.5 でも差はない。

### 3-7. 読めない写真では、どのモデルも推測せず `unreadable` を返した（L003）

袋の曲面・斜め・小さい文字が重なった L003 は、**全モデルが `unreadable` を返し、数値を1つも推測で埋めなかった**。Opus 5.5 は2列のエネルギーをおおよそ読めていた（正解の 250kcal・289kcal と同じ）が、確信がないとして null にした。これはプロンプトの「推測で埋めない」に沿った安全側の失敗で、誤った値が記録されるより望ましい。

- **上位モデルに変えても救えなかった**ので、この条件ではモデル選びの差は出ない
- **正面から撮り直すと、Haiku 5.5 で全項目を正しく読めた**。読めないときは、アプリで「正面から近づけて撮り直す」よう案内するのが有効

### 3-8. 味違いの2列表示は、今のプロンプトで想定していない

L003 の表示は「1個当たり」でシュガー味・チョコ味の2列。プロンプトの「複数の表示があるときは1包装全体に近い方を選ぶ」は、1個当たりと1袋当たりのような**基準違いの2列**を想定した規則で、**味違いの2列**には当てはまらない。撮り直し写真では、Haiku 5.5 は先頭（シュガー）の列を採用し、もう1列の値を notes に書いた。どちらの袋かは写真から分からないことが多いので、アプリでは利用者に選んでもらう必要がある。今の出力スキーマは1列分しか返せない（→ 次にやること 3）。

### 3-9. 「1個当たり」の基準量の返し方が揺れた

撮り直し写真で、Haiku 5.5 の low は `amount: null`、medium は `amount: 1`（unit は null）と返した。どちらも「1個当たり」の意味だが、コードで扱うには1つに決める必要がある。`per_piece` のときは amount を null にする、と意味上のルールに加えるのがよい。

## 4. 所見

- **精度**: 読める写真（4枚中3枚）では全モデルが kcal・P・F・C をすべて正しく読んだ。読めない写真では全モデルが推測せず `unreadable` を返した。合格の目安（条件のよい写真で 95% 以上）は満たす見込み。ただし枚数が少ない（4枚）ので、MVP 実装後も実データで見続ける
- **モデル**: **Haiku 5.5（effort low）を第一候補**とする。厳しい条件でも Sonnet・Opus との差は出ず、費用は Sonnet の約20分の1、Opus の約40分の1
- **画像**: 長辺 1024px 以上に縮小する
- **アプリの流れ**: `unreadable` のときは撮り直しの案内が要る。味違いなど複数列の表示は、利用者に列を選ばせる仕組みが要る

## 5. 次にやること

1. **モデルと画像サイズを ADR に残す**: OCR は Haiku 5.5・effort low・長辺 1024〜1568px（Q-24。ユーザーの了承を得てから）
2. **`unreadable` のときの流れを決める（Q-25）**: Q-15 では「エラーダイアログ → 入力方法の選択に戻る」と決めた。そこに「撮り直す」ボタンと撮り方の案内（正面から・近づけて）を加えるか
3. **複数列の表示の扱いを決める（Q-26）**: 出力スキーマで全列を返し（例: `columns` 配列）、利用者が選ぶ形にするか。→ 対応済み: 出力スキーマ v0.3・プロンプト 0.2.0。採点は正解に最も合う列で行う（利用者が正しい列を選ぶ想定）
4. **意味上のルールを足す**: `per_piece` のとき `basis.amount` は null。→ 対応済み（contracts/llm/README.md、契約テスト）
5. **栄養成分表示でない写真で `not_nutrition_label` を確かめる**（Haiku 1〜2回、1円未満。写真は手元の work/写真 にあるキーボードの写真を使える）
6. **個数で売られている商品の分量の既定を決める（Q-27）**: ドーナツは「1個当たり」・4個入り。Q-14 の既定「全部食べた」だと4個分になる。既定を「1個」にしてワンタップで個数を選ぶか
7. プロンプトキャッシュの効果を確かめる（POC-44）

> 2026-11-13 決定: 1 → ADR-0010（Q-24）、2 → 撮り直すボタンと案内を加え、方式選択に戻るも残す（Q-25）、3 → 全列を返して利用者が選ぶ（Q-26）、6 → 既定は「1個」（Q-27）。反映先は [scope.md](../../docs/01_requirements/scope.md)
