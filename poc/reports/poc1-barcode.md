## 1. 条件

| 項目 | 内容 |
|---|---|
| 商品DB | Open Food Facts（API v2、`world.openfoodfacts.org`） |
| サンプル | 5件（`poc/samples/barcode/ground_truth.csv`）。計画は30点前後だったが、収集が難しいため5件で検証する（ユーザー決定） |
| 換算方法 | Open Food Facts の 100g 当たりの値を、**正解データの基準量**（1包装当たりなら内容量）で換算して比べる |

## 2. 結果

| 指標 | 結果 | 合格の目安 |
|---|---|---|
| ① 見つかった割合 | 5/5（100%） | — |
| ② 見つかった中で 4項目（kcal・P・F・C）がそろう割合 | 5/5（100%） | — |
| **①×② 使える割合** | **5/5（100%）** | 50% 以上で主力として採用 |

### B003 が一致しなかった原因

Open Food Facts に、**1食（76g）当たりの値（354kcal など）が「100g 当たり」として登録されていた**。4項目すべてが正解のちょうど 0.76 倍（76g/100g）になっていることと、取得したデータそのもので確認した。スクリプトの誤りではなく、誰でも編集できるデータベースの登録ミス。

この誤りは、栄養値の組み合わせ（P×4＋F×9＋C×4 ≒ kcal）では検出できない（値そのものは整合しているため）。アプリ側で自動的に見抜くのは難しい。

## 3. 分かったこと

1. **見つかる割合は高い**（5/5）。国内の大手メーカー品は Open Food Facts に登録されていることが多い可能性がある（ただしサンプルの偏りに注意）
2. **栄養値はおおむね正確だが、登録ミスがある**（5件中1件）。誤った値がそのまま記録されるリスクがある
3. **内容量（`product_quantity`）はほとんど登録されていない**（1/5）。しかし **1食分の量（`serving_quantity`）は 4/5 で登録されており、すべて正解の内容量と一致した**。1個売りの商品なら「1食分の量 ＝ 1包装 ＝ 全部食べた量」として使える可能性が高い
4. 1食分の量は複数個入りの商品（例: 6個入りの菓子）では内容量と一致しないはず。今回のサンプルには含まれていないので未検証
5. ml の商品も 100g 当たりで登録されている。B001 で 1ml＝1g とみなした誤差は kcal で約2%（許容範囲内）

## 4. 暫定判定（ユーザーの了承待ち: Q-22）

**条件付きで採用**（MVP の入力方式として残す）。

- 合格の目安（①×② ≥ 50%）は満たしている（5/5）。ただしサンプルが5件で偏りもあるため、結論は暫定とする
- 採用の条件:
  - **確認画面で値の出どころ（Open Food Facts）を表示し、ワンタップで OCR（栄養成分表示の撮影）に切り替えられるようにする**（登録ミス対策）
  - **全部食べた量は「内容量 → なければ 1食分の量」の順で決める**。どちらもなければ、別の手段が必要（Q-23）
- 実際に使いながら一致しない商品を記録し、件数が増えたら見直す

## 5. 次にやること

1. 暫定判定（Q-22）と、内容量が取れない場合の扱い（Q-23）を決める → ADR と scope.md に反映
2. PoC-2（栄養成分表示 OCR）: 写真2枚は用意済み。Claude API の実行が必要（費用は2枚なら十数円程度の見込み。実行前に了承を得る）
3. 余裕があれば、複数個入りの菓子・飲料などを数件追加して、1食分の量の扱いを確かめる（CSV に行を足して再実行するだけ）

## 6. 実行方法

```bash
wsl -e bash -lc "cd /mnt/c/project/onaka-log && UV_LINK_MODE=copy ~/.local/bin/uv run --group poc python poc/poc1-barcode/run.py"
```
