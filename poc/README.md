# PoC 計画（機能1〜3）

> ステータス: Draft
> 最終更新: 2026-11-12
> 関連: roadmap POC-01〜POC-44、LLM-03、TST-03、[scope.md](../docs/01_requirements/scope.md)、[ADR-0001](../docs/adr/0001-spec-driven-and-test-driven.md)

## 1. 目的

アプリを作る前に、MVP の入力方式（バーコード・栄養成分表示 OCR・写真推定）が **「人が入力しなくても使える精度・速度・コスト」** で動くかを確かめる。結果によってはスコープや UX（分量の決め方、失敗時の扱い）を見直す。

あわせて、Claude API の入出力スキーマ（`contracts/llm/`）を実データで検証し、初版を固める。

## 2. 進め方の原則

- **アプリは作らない**。WSL 上の Python スクリプトで、手元のサンプルを使って検証する
- サンプル画像は**スマホで実際に撮ったもの**を使う（ネットの綺麗な画像では実態とずれる）
- Claude には `contracts/llm/<usecase>/` のスキーマと `prompt.md` をそのまま使わせる。PoC 中にスキーマを直したら、契約テスト（`tests/contract/`）を通してから使う
- 仕様駆動・TDD の規律（ADR-0001）は PoC には適用しない（速度優先）。ただし結果は `poc/reports/` に、確定したスキーマ・プロンプトは `contracts/` に残す
- 画像は Git に入れない（ADR-0004 の趣旨。`.gitignore` 済み）。正解データの CSV は Git で管理する
- **Claude API の実行は費用がかかるので、各回の実行前に件数と概算費用を出し、ユーザーの了承を得る**（§8）

## 3. 検証項目と合格基準

基準は目安。結果を見て、ユーザーと相談のうえで判断する（§9）。

### PoC-1: バーコード照合（POC-11〜14）

| 項目 | 内容 |
|---|---|
| 確かめたいこと | 普段買う国内の商品が商品DBで見つかり、カロリー・PFC と**内容量**がそろっているか |
| 商品DB | まず Open Food Facts（無料・API キー不要）。結果が悪ければ他の候補を調べる（POC-11） |
| 計測 | ①見つかった割合 ②見つかった中で 4項目（kcal・P・F・C）がそろう割合 ③内容量が取れる割合 ④値の基準（100g 当たり／1食当たり）の内訳 ⑤パッケージ表示との一致（各値が ±5% 以内） |
| 合格の目安 | ①×②が **50% 以上**なら主力として採用。**20% 未満**なら主力にせず、見つからないときは OCR へ誘導する前提で設計する |
| 比べ方（2026-11-13 決定） | Open Food Facts の 100g 当たりの値を、**正解データの基準量**で換算して比べる。一致は kcal が ±5%（最低 ±5kcal）、P・F・C が ±5% と ±0.5g の広い方。Open Food Facts に内容量があるかは ③ で別に集計する |
| Claude 使用 | なし |
| 結果 | [reports/poc1-barcode.md](reports/poc1-barcode.md)（2件で動作確認済み、判定保留） |

> Open Food Facts の API は、利用者を識別できる User-Agent を付けるよう求めている。個人情報は入れず、`onaka-log-poc/0.1` のような汎用の名前にする。

### PoC-2: 栄養成分表示 OCR（POC-21〜24）

| 項目 | 内容 |
|---|---|
| 確かめたいこと | 栄養成分表示の写真から、kcal・P・F・C・基準量・内容量を正しく読み取れるか |
| 方式 | Claude Vision に画像を直接渡し、Structured Outputs で JSON を返させる。端末 OCR との比較（POC-21）は、この方式が基準に届かなかった場合だけ行う |
| 計測 | ①項目ごとの正答率（kcal・P・F・C）②基準量の読み取り正答率 ③内容量の読み取り正答率 ④誤読のパターン ⑤撮影条件（正面・斜め・反射・曲面・小さい文字）ごとの正答率 ⑥応答時間 ⑦1回あたりの費用 |
| 正答の定義 | 表示された数値と一致（小数の表記ゆれは正規化してから比較） |
| 合格の目安 | kcal・P・F・C の正答率が、条件のよい写真で **95% 以上**、全体で **85% 以上**。読み取れない写真では `status` が `unreadable` になる（誤った値を返さない） |

### PoC-3: 写真からの推定（POC-31〜34）

| 項目 | 内容 |
|---|---|
| 確かめたいこと | 料理の写真から、料理名・量・kcal・PFC を「確認画面で軽く直せば済む」精度で推定できるか |
| 計測 | ①kcal の誤差率（\|推定−正解\|/正解）の中央値 ②P・F・C の誤差率の中央値 ③料理名の妥当性（目視で ○/△/×）④同じ写真を3回推定したときのばらつき（kcal の変動係数）⑤1枚に複数の料理がある場合の分解の妥当性 ⑥食べ物でない写真やぼやけた写真での `status` |
| 合格の目安 | kcal の誤差率の中央値が **30% 以内**、かつ誤差 30% 以内に入る割合が **60% 以上**。3回推定の変動係数が **10% 以内** |

### PoC-4: テキスト推定（任意・簡易）

テキスト入力も MVP に入ったため、PoC-3 の正解データに料理の説明文（例:「から揚げ定食、ご飯大盛り」）を付けて簡易に確かめる。基準は PoC-3 と同じ。サンプルを別に集める必要はない。

### 横断（POC-41〜44）

| 項目 | 内容 |
|---|---|
| モデル比較 | Haiku 5.5 / Sonnet 5.5 / Opus 5.5。effort は `low` と `medium` を比べる。精度・応答時間・費用で選ぶ |
| 画像の縮小 | 長辺 768 / 1024 / 1568 px で、精度・応答時間・入力トークン数を比べる。Lambda の 6MB 上限（ADR-0007）に収まるサイズも確認する |
| 費用 | 1回あたりの費用を実測し、月の想定利用回数での費用を見積もる（NFR-001: 月1000円） |
| プロンプトキャッシュ | 固定のシステムプロンプトでキャッシュが効くか（`cache_read_input_tokens`）を確認する |
| 応答時間 | p50 / p90。体感で許容できるかの目安は p50 **5秒以内** |

## 4. サンプルと正解データ

### 件数

| 種類 | 件数の目安 | 選び方 |
|---|---|---|
| バーコード | 30点前後 | コンビニ・スーパーで普段買うもの。飲料・パン・弁当・菓子・冷凍食品・調味料など種類を散らす |
| 栄養成分表示の写真 | 20枚前後 | PoC-1 と同じ商品でよい。正面・斜め・反射・曲面・小さい文字、「100g 当たり」と「1包装当たり」が混ざるように |
| 料理の写真 | 20〜30枚 | 正解が分かるもの（栄養表示付きの弁当・総菜、重さを量った自炊など）。1品だけの写真と、複数品が写った写真（定食など）の両方 |
| 異常系 | 5枚前後 | 食べ物でない写真、ひどくぼやけた写真、栄養成分表示が半分切れた写真 |

## 5. 実行環境

| 項目 | 内容 |
|---|---|
| 実行場所 | WSL（Ubuntu）、リポジトリは `/mnt/c/project/onaka-log` |
| Python | uv で管理（Lambda に合わせて 3.12 を想定）。仮想環境はリポジトリ直下の `.venv`（Git 管理外） |
| 主なライブラリ | `anthropic`（公式 SDK）、`jsonschema`、`pillow`（画像の縮小）、`httpx`（Open Food Facts）、`pytest` |
| API キー | `ANTHROPIC_API_KEY` を `.env` に置く（Git 管理外）。キーは画面やログに出さない |
| 呼び出し方 | SDK の Structured Outputs（`output_config.format`）で `contracts/llm/<usecase>/output.schema.json` を指定する。SDK が API 未対応の制約（`minimum` など）を取り除いて送り、受け取った出力をクライアント側で検証する。さらにスクリプト側で、完全版のスキーマで `jsonschema` 検証する |

poc/

## 8. 費用の見積りと上限

| 実行 | 回数の目安 | 概算 |
|---|---|---|
| PoC-2 モデル比較（20枚 × 3モデル × effort 2種） | 120回 | 約 250円 |
| PoC-3 モデル比較＋ばらつき（25枚 × 3モデル × 3回） | 225回 | 約 500円 |
| 画像サイズ比較（45枚 × 3サイズ、1モデル） | 135回 | 約 270円 |
| PoC-4 テキスト（25件 × 3モデル） | 75回 | 約 50円 |
| **合計** | 約 550回 | **約 1,100円** |

- 概算は non-functional.md の単価（Sonnet 5.5 で1回約2円）から出した。画像サイズやモデルの組合せで変わる
- **PoC 全体の上限は 2,000円** とし、超えそうなら止めて相談する
- 各実行の前に、スクリプトで件数と概算費用を表示し、了承を得てから実行する

## 9. 結果に応じた判断

| 結果 | 対応 |
|---|---|
| バーコードの見つかる割合が低い | バーコードは「見つかればラッキー」の扱いにし、見つからないときは OCR へ誘導する UX にする |
| 内容量が取れないことが多い | 「全部食べた」の換算ができないため、分量の決め方（scope.md）を見直す |
| OCR の精度が不十分 | 撮影ガイドの追加、プロンプトの改善、端末 OCR との比較（POC-21） |
| 写真推定の誤差が大きい | 「目安値」と明示して残す。確認画面で修正しやすくする |
| 応答が遅い | 小さいモデル・低い effort・画像の縮小。待ち時間の UX（推定中の表示）を工夫する |
| 費用が高い | モデル選定の見直し、ユーザーごとの回数制限（LLM-10） |

## 10. PoC でやらないこと

- アプリの UI・端末でのバーコード読み取り（Expo のライブラリで実績があるため。実機では実装時に確認: POC-14）
- バックエンド（Lambda・Cognito・DynamoDB）
- 端末 OCR（§3 PoC-2 の条件を満たさない場合のみ）
