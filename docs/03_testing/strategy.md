# テスト戦略

> ステータス: Draft
> 最終更新: 2026-11-14
> 関連: TST-01, TST-02, TST-04〜TST-11, ADR-0001, [traceability.md](traceability.md), [folder-structure.md](../00_project/folder-structure.md)

## 1. 考え方

- **仕様駆動 + テスト駆動**（ADR-0001）。仕様（docs）→ 契約（contracts）→ テスト（赤）→ 実装（緑）の順に進める
- 目標は「**このテストが通るまで実装して**」と頼める状態。そのため、実装の前に、仕様の ID と結びついたテストが揃っていることを重視する
- 決まった振る舞い（計算・ルール・API の形）は速いテストで厚く守り、遅く壊れやすいテスト（実機・実 API）は薄くする
- Claude の出力は毎回少し変わる。通常のテストでは**記録した応答**を使い、実際の API は費用の上限を決めて別に動かす

## 2. テストの層

| 層 | 置き場所 | 何を確かめるか | 道具 | いつ動かす |
|---|---|---|---|---|
| ① 契約テスト | `tests/contract/` | スキーマ・OpenAPI の正しさ、例の適合・不適合、ルールの参照実装（`domain_rules.py`・`api_rules.py`）が仕様どおりか | pytest、jsonschema、openapi-spec-validator | 毎回（CI） |
| ② バックエンドの単体テスト | `apps/api/tests/unit/` | ドメインの計算とルール（DM-01〜09）、Claude の出力から候補への変換、Open Food Facts の応答の変換、設定 | pytest | 毎回（CI） |
| ③ バックエンドの API テスト | `apps/api/tests/api/` | FastAPI のルートが OpenAPI の契約どおりに動くか（状態コード・本文の形・エラーコード・認可）。DB を含む一連の流れ | pytest、FastAPI の TestClient、DynamoDB Local | 毎回（CI） |
| ④ モバイルの単体・部品テスト | `apps/mobile/`（置き方は TEC-08） | 値のプレビュー計算、分量の選択、エラー文言の対応、画面の部品の振る舞い | Jest 系（TEC-08 で決める） | 毎回（CI） |
| ⑤ インフラの検査 | `infra/` | SAM テンプレートの正しさ | `sam validate`、cfn-lint | 毎回（CI） |
| ⑥ dev 環境での確認 | — | Lambda 固有の部分（認証・6MB 上限・タイムアウト・IAM）、アプリとの結合 | 手動＋簡単なスクリプト | デプロイ後 |
| ⑦ E2E | `tests/e2e/` | アプリの主な流れ（記録して一覧に出る） | TST-08 で決める（Mac がないため Android エミュレーター前提） | リリース前（手動トリガー） |
| ⑧ 実 API のスモーク | `tests/eval/`（smoke） | 本物の Claude・Open Food Facts で、契約どおりに返るか | pytest（マーカーで分ける） | 手動、モデル・プロンプト変更時 |
| ⑨ LLM の回帰評価（eval） | `tests/eval/` | プロンプト・モデルを変えたときに精度が落ちていないか | PoC のスクリプトを流用 | 手動、変更時 |

テストの量は ①〜④ が大半。⑥〜⑨ は少数で、費用・時間がかかるものは手動で動かす。

## 3. 層ごとの方針

### 3-1. ドメインのルール（② と ① の関係）

- ルールの正は `docs/02_design/domain-model.md` §6（DM-01〜09）。契約テストの `tests/contract/domain_rules.py` は**参照実装**
- バックエンドのドメイン（`apps/api/src/onaka_api/domain/`）は参照実装を import せずに独立に書き、**同じ例（`contracts/domain/examples/`）で同じ結果になる**ことを単体テストで確かめる（例ファイルが2つの実装をつなぐ）
- 計算の境界（4:00 の境目、四捨五入、単位が合わない内容量、個数売り）は表形式のテスト（`pytest.mark.parametrize`）で書く

### 3-2. Claude を使う部分（TST-04・TST-05・TST-07）

| 種類 | 中身 |
|---|---|
| 記録した応答（フィクスチャ） | PoC で得た Claude の出力（JSON、画像は含まない）を `apps/api/tests/fixtures/llm/<用途>/` に置く。単体テストは Claude の呼び出しを差し替えて、これを返す |
| 失敗の再現 | リフューザル・出力の途切れ（`max_tokens`）・スキーマ違反・意味ルール違反・タイムアウト・429 を、差し替えで再現して 422 / 502 / 429 になることを確かめる |
| 実 API のスモーク（⑧） | `@pytest.mark.live`。既定では動かさない（`-m live` のときだけ）。1回の実行で数円以内（Haiku 中心、写真は Sonnet を1回）。キーは `.env` |
| 回帰評価（⑨） | PoC のサンプル（`poc/samples/`、画像は Git 管理外）と PoC のスクリプトを使う。OCR は4項目の正答、写真は品目数・ばらつき（CV）・PoC の結果との差を見る。プロンプト・モデルを変えるときに実行し、結果を `poc/reports/` か `docs/03_testing/` に残す |

### 3-3. API（TST-06）

- ③ の API テストでは、**応答の本文を `contracts/api/openapi.yaml` のスキーマで検証する**（契約テストと同じ仕組みで `$ref` を解決する）
- 契約にあるすべての操作（9つ）に、正常と主なエラーのテストを1つ以上置く
- FastAPI が出す OpenAPI と契約の「パスとメソッドの一覧」が一致することもテストする（実装漏れ・余分な API を防ぐ）

### 3-4. データとフィクスチャ（TST-09）

- 画像は Git に入れない（ADR-0004 の考え方と同じく、テストでも実画像を持ち回らない）。単体・API テストは画像の代わりに小さなダミー（数バイトの JPEG）と記録した応答を使う
- 実画像が要るのは ⑧・⑨ だけで、手元の `poc/samples/` を使う
- DynamoDB Local はテストごとにテーブルを作り直す

## 4. カバレッジ（TST-10）

- 行カバレッジの数値目標は置かない（数値合わせのテストを避ける）
- 代わりに **仕様の ID が少なくとも1つのテストに結びついていること** を確かめる（[traceability.md](traceability.md)）。MVP の範囲では DM-01〜09 と MVP の機能（F-xxx）が対象
- バックエンドの `domain/` だけは行カバレッジも見る（計算の分岐の抜けを見つけるため。目安 90%）

## 5. 「テスト先行 → 実装」の手順（TST-11、HNS-03）

1. **仕様**: 機能の詳細仕様（`docs/01_requirements/features/F-xxx-*.md`）に要件を `F-xxx-01` のように書く
2. **契約**: 必要なら `contracts/` を変え、契約テストを通す
3. **テスト（赤）**: 要件 ID の `spec` マーカーを付けたテストを書き、**失敗することを確かめてから**コミットする（「テスト: F-xxx-01〜03 を追加（赤）」）
4. **実装（緑）**: テストが通るまで実装する。実装の段階では、テストと契約を変えない（CLAUDE.md）。変える必要が出たら止めてユーザーに確かめ、仕様 → 契約 → テストの順に直す
5. **確認**: `tools/trace.py --check` で、仕様の ID とテストの対応に抜けがないことを確かめる
