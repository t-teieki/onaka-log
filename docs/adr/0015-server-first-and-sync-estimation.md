# ADR-0015: 記録はサーバーファースト、推定は同期 API、計算はバックエンド

- ステータス: Accepted
- 日付: 2026-11-14
- 関連: Q-35, ARC-01, ARC-02, ARC-07, REQ-17, DAT-09, ADR-0009, ADR-0013, [architecture.md](../02_design/architecture.md)

## 背景

全体構成（ARC-01）を描くにあたり、記録データの置き場所（ARC-02）、推定を同期で返すか（ARC-07）、計算や外部 API 呼び出しをどこで行うかを決める必要がある。

## 決定

1. **サーバーファースト**: 記録の正は DynamoDB。アプリは表示のために一時的に持つだけで、端末 DB と同期は MVP では作らない。オフラインでは記録・閲覧できない（REQ-17）
2. **推定は同期 API**: OCR・写真推定はリクエストの中で Claude を呼び、結果を返す。ジョブ化・ポーリングはしない（PoC の応答は OCR 約4秒、写真 p90 約5秒で、API Gateway の上限 30秒に収まる）
3. **推定と保存は別の API**: 推定結果は保存せず、利用者が確認画面で確かめた後に保存 API を呼ぶ
4. **計算はバックエンド**: 倍率・食べた量の値・合計の計算と、ドメインのルール（DM-01〜08）の検証はバックエンドで行う。アプリから送られた計算値は使わない
5. **Open Food Facts はバックエンドから呼ぶ**: ADR-0009 の換算規則をバックエンドに集め、利用規約（User-Agent など）をまとめて守る

## 理由と影響

- 推定はどれもオンラインが必要で、オフラインで完結するのは手入力だけ。同期と競合解決（DAT-09）を作る手間に見合わない
- ID をアプリで作る（ADR-0013）ので、将来オフラインの手入力を足すときも大きな作り直しは要らない
- 計算をバックエンドに集めると、ルールを1か所で検証でき、アプリを古い版のまま使う利用者がいても記録の値がそろう
- 見直す条件: オフラインでの記録の要望が強くなった場合、写真推定の応答が 20秒を超えるようになった場合（ジョブ化を検討）
