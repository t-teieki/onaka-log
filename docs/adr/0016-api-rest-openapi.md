# ADR-0016: API は REST + OpenAPI 3.1、パスで版を分ける

- ステータス: Accepted
- 日付: 2026-11-14
- 関連: ARC-04, ARC-08, ARC-09, ADR-0001, ADR-0007, ADR-0015, [api.md](../02_design/api.md)

## 背景

アプリとバックエンドの API の形を決める。バックエンドは FastAPI（ADR-0007）、契約は機械可読にして SSOT とする（ADR-0001）。モバイルアプリは古い版が残るため、版の扱いが要る。

## 選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| REST + OpenAPI | FastAPI と相性がよい。API Gateway HTTP API の作りに合う。クライアントコードを生成できる | 画面ごとに必要なデータをまとめにくいことがある |
| GraphQL | 画面ごとに取りたいデータを選べる | サーバー・キャッシュ・認可が複雑。今回の API は小さい |
| RPC（gRPC など） | 型が厳密 | モバイル・API Gateway での扱いが手間 |

## 決定

1. **REST + OpenAPI 3.1**。契約は `contracts/api/openapi.yaml` に書き、食品の元の値・出どころなどは `contracts/domain/meal.schema.json` を参照する（二重に定義しない）
2. **版はパスで分ける**（`/v1`）。互換を壊す変更は `/v2` を作り、古いアプリのために `/v1` を一定期間残す。項目の追加など互換を保つ変更は同じ版で行う
3. **エラーは `{"error": {"code", "message"}}`** で返し、画面の文言はアプリが `code` から決める（ARC-08）。読めない・見つからないなどの推定結果は HTTP 200 の `status` で返す

## 理由と影響

- 実装時は、FastAPI が出す OpenAPI と契約を比べるテストで準拠を確かめる（TST-06）
- アプリ側の型は OpenAPI から生成する（TEC-07 で道具を決める）
- 見直す条件: 画面ごとの取得が増えて API の呼び出し回数が問題になったら、まとめ用のエンドポイントを足す
