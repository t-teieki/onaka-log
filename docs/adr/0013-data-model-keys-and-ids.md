# ADR-0013: 食事のキー・ID・値の持ち方

- ステータス: Accepted
- 日付: 2026-11-14
- 関連: DAT-01〜DAT-08, Q-31〜Q-33, ADR-0008, [domain-model.md](../02_design/domain-model.md), [data-model.md](../02_design/data-model.md)

## 背景

ADR-0008 で DynamoDB を選び、食品（FoodItem）を食事（Meal）に埋め込む方針にした。アクセスパターン（[data-access-patterns.md](../02_design/data-access-patterns.md)）と Q-31〜Q-33 の決定を受けて、キー・ID・値の持ち方を決める。

## 選択肢

| 論点 | 選択肢 | 選んだもの |
|---|---|---|
| テーブル | 種類ごとに分ける / 1テーブル | 1テーブル（将来の日次サマリなども同じテーブルに入れる） |
| ソートキー | `記録日#時刻` / `MEAL#記録日#時刻#食事ID` | 後者。同じ時刻の食事を区別でき、種類の接頭辞で将来の種類と分けられる |
| ID | DB の連番 / サーバーで UUID / アプリで UUIDv7 | アプリで UUIDv7。再送しても同じ ID になり、二重保存を条件付き書き込みで防げる |
| 値の持ち方 | 食べた量の値だけ / 元の値と分量と食べた量の値 | 3つとも持つ。どう計算したかを後から確かめられ、確認画面の「内容量：不明」などを出せる |
| 合計 | 読むたびに計算 / 書き込み時に計算して保存 | 書き込み時に保存（ADR-0008 の第一案） |
| 同時更新 | 何もしない / `version` による楽観的ロック | 楽観的ロック（食品の追加・削除は読み→書きになるため） |
| 削除 | 論理削除 / 物理削除 | 物理削除（保存後の修正・履歴を持たないため、Q-31） |

## 決定

上の表の「選んだもの」のとおり。属性の詳細は [contracts/domain/meal.schema.json](../../contracts/domain/meal.schema.json) を正とする。

## 理由と影響

- MVP のアクセスパターンは、`Query` 1回（1日分）と `GetItem` / `PutItem` / `UpdateItem` / `DeleteItem` だけで済む
- 食べた日時を保存後に変えない（Q-33）ので、ソートキーは作成後に変わらない。将来日時の変更を許すなら、削除して作り直す処理が要る
- 元の値と倍率を残すので、分量の規則（ADR-0009、Q-27）を変えたときも、過去の記録がどう計算されたかを確かめられる
- 見直す条件: 推移グラフ（AP-09）・よく食べる食品（AP-10）を作るとき、日次サマリのアイテムや GSI を足す
