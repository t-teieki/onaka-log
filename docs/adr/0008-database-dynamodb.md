# ADR-0008: DB は DynamoDB

- ステータス: Accepted
- 日付: 2026-11-11
- 関連: Q-21, TEC-06, DAT-01, DAT-02, ADR-0007, [比較資料 C-1〜C-3](../../議論/バックエンド構成/バックエンド構成比較.md)

## 背景

バックエンドは AWS サーバーレス（ADR-0007）。DB の候補は DynamoDB と、Lambda から Supabase の Postgres を使う案があった。

## 決定

DynamoDB を使う。

## 理由

- AWS だけで完結し、管理する場所が1つで済む
- Supabase 無料枠のような一時停止のリスクがない
- 少量なら無料枠の範囲で、月1000円（NFR-001）に収まる
- MVP に必要な集計（日次合計・食事ごとの合計）は、キーでの範囲検索とコードでの合計で無理なく書ける

## データ設計の初期方針（詳細は DAT-01・DAT-02 で決める）

- **Meal の中に FoodItem を配列で埋め込む**のを第一案とする。食事合計は書き込み時に計算して Meal に保存する
- キー案: パーティションキー `userId`、ソートキー `4時補正後の日付#時刻`（例: `2026-11-11#12:00`）。1日分を範囲検索で取れ、4:00 境界も扱いやすい
- 週・月の推移（MVP 外）が必要になったら、日次サマリのアイテムを追加し、食事の更新と同じトランザクションで更新する

## 影響・注意点

- DynamoDB には SQL の `GROUP BY` / `SUM` がない。後から集計の種類を増やすとキー設計の見直しが必要になることがあるので、アクセスパターンを先に洗い出してから設計する（DAT-01）
- 食品名での横断検索は苦手（GSI の追加が必要）。食品検索（EXT-05）を作る段階で再検討する
- ローカル開発には DynamoDB Local（Docker）が使える
- 「ORM・マイグレーションツール」は不要になる。代わりにアイテムの形を JSON Schema（`contracts/domain/`）で定義し、読み書き時に検証する
