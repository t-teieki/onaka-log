# データのアクセスパターン（DAT-00）

> ステータス: Draft（キー設計の前提。キーと属性の確定は DAT-01 ドメインモデル・データモデルで行う）
> 最終更新: 2026-11-14
> 関連: DAT-00, DAT-01, DAT-02, [ADR-0008](../adr/0008-database-dynamodb.md), [機能一覧](../01_requirements/features/README.md), Q-31〜Q-33

DynamoDB は後から集計の種類を増やすとキー設計の見直しが要る（ADR-0008）。そのため、機能（F-xxx）から読み書きのパターンを先に洗い出す。

## 1. 前提

- 読み書きはすべてサインインした利用者本人のデータだけ（他人のデータを読む機能はない）
- 1日の境界は 4:00、日本時間に固定（Q-33）。食べた日時から 4時間引いた日付を「記録日」とする（例: 11/14 02:30 の食事は 11/13 の記録）
- 食べた日時は確認画面で決め（既定は記録した時刻、過去も可）、保存後は変えない（Q-33）。保存した食品の値も変えない（Q-31）
- 食事（Meal）1件に食品（FoodItem）N件。ADR-0008 の第一案どおり、食品は食事の中に配列で埋め込み、食事の合計は書き込み時に計算して食事に保存する
- 規模の目安: 1人1日 3〜6食、1食 1〜6品目。1食事のアイテムは数 KB で、DynamoDB の上限（400KB）に十分収まる

## 2. アクセスパターン

| ID | パターン | 機能 | 区分 | 頻度 | 読み書き | 条件・返すもの |
|---|---|---|---|---|---|---|
| AP-01 | 1日分の食事と合計を取る | F-031 | MVP | 高（アプリを開くたび） | 読み | 利用者・記録日 → その日の食事（食品を含む）を時刻順に。日次合計は食事の合計をコードで足す |
| AP-02 | 食事を保存する（食品 N件ごと） | F-030 | MVP | 中（1日 3〜6回） | 書き | 食品ごとの値・基準・内容量・出どころ・推定情報（モデルID・prompt_version・スキーマのバージョン）と、食事の合計を1回で書く |
| AP-03 | 食事1件を取る | F-020, F-032 | MVP | 中 | 読み | 利用者・食事ID → 食事（食品を含む） |
| AP-04 | 食事を削除する | F-032 | MVP | 低 | 書き | 利用者・食事ID |
| AP-05 | 食事から食品を1件削除する | F-032 | MVP | 低 | 書き | 食品の配列から外し、食事の合計を計算し直して更新する。最後の1件なら食事ごと削除する（Q-31） |
| AP-06 | 既存の食事に食品を足す | F-030 | MVP | 中 | 書き | 食品を配列に追加し、食事の合計を更新する（Q-32） |
| AP-07 | 保存した食品の値を直す | F-020 | 廃止（MVP ではしない） | — | — | Q-31 で MVP では行わないと決めた。将来入れるなら、食品を更新し合計を更新する |
| AP-08 | 利用者のデータをすべて削除する | F-002 | 公開前 | まれ | 書き | 利用者の全アイテムを削除する（アカウント削除） |
| AP-09 | 期間の日次合計を取る（週・月） | F-040 | 次期 | 中 | 読み | 利用者・期間 → 日ごとの合計。日次サマリのアイテムを足すか、食事を範囲で読んで足すか（ADR-0008） |
| AP-10 | よく食べる食品・最近の食品を取る | F-042 | 次期 | 中 | 読み | 利用者 → 食品名ごとの回数・最終日時 |
| AP-11 | 記録日の一覧（記録がある日）を取る | F-031 | 未決 | 低 | 読み | カレンダーなどで記録のある日を示すなら必要。MVP の画面次第（UIX） |

## 3. キー設計の見通し（ADR-0008 の案で足りるか）

ADR-0008 の案: パーティションキー `userId`、ソートキー `記録日#時刻`（例: `2026-11-13#12:30`）。

| パターン | この案での実現 | 評価 |
|---|---|---|
| AP-01 1日分 | `userId` ＝ 利用者 かつ ソートキーが `2026-11-13#` で始まる、の範囲検索（Query 1回） | ◎ |
| AP-02 保存 | PutItem 1回（食品は埋め込み、合計も同じアイテム） | ◎ |
| AP-03・04・05・06・07 | 食事を特定するのにソートキー（記録日#時刻）が要る。食事ID だけで引くなら工夫が要る | △ → 下記 |
| AP-08 全削除 | `userId` で Query して全件を消す（件数が多ければ分けて） | ○ |
| AP-09 期間 | ソートキーの範囲検索（`2026-11-01` 〜 `2026-11-30`）で食事を読み、コードで日ごとに足す。数か月分なら日次サマリのアイテムを足す | ○（MVP 外） |
| AP-10 よく食べる食品 | この案では全件を読むことになる。次期で別のアイテム（食品ごとの集計）か GSI を足す | △（MVP 外） |

**食事の特定方法（△への対応案）**:
- ソートキーを `記録日#時刻#食事ID`（例: `2026-11-13#12:30#01J...`）にし、アプリは一覧（AP-01）で得たソートキーを持ったまま詳細・削除・更新を行う。同じ時刻の食事が2件あっても区別できる
- 保存後に食べた日時を変えないので（Q-33）、ソートキーは作成後に変わらない

## 4. 決定事項（2026-11-14）

| ID | 決定 | 影響するパターン |
|---|---|---|
| Q-31 | 保存した食品の値は直さない。食品が0件になった食事は自動で削除する | AP-05, AP-07（廃止） |
| Q-32 | 後から同じ食事に食品を足せる。食事区分は持たない | AP-01, AP-06 |
| Q-33 | 日時は確認画面で決め、保存後は変えない。日本時間に固定 | AP-01, AP-02, ソートキー |

## 5. 次にやること

1. DAT-01 ドメインモデル（Meal / FoodItem / 値の基準・内容量・出どころ・推定情報）とデータモデル（キー・属性・JSON Schema `contracts/domain/`）を書く
2. DAT-02（合計の持ち方）は ADR-0008 の第一案（書き込み時に計算して保存）で進め、DAT-01 で確定する
